## 1. Scope

This is the second Phase 1C spike. It addresses R-012, R-014, R-031 and R-032:

- duplicate/replayed operation requests;
- per-instance and shared-resource concurrency;
- preservation of the validated plan fingerprint;
- cooperative cancellation;
- active-operation tracking;
- controlled process shutdown.

It is independent of Pode and of PR #38. It does not define the final REST contract or engine contract.

## 2. Architecture constraints

[CONFIRMED] ADR-0007 says V1 writes no state database: operation history goes to text logs and locks/idempotency tokens are in memory.

[CONFIRMED] ADR-0001 says the process is interactive/transient, V1 is single-operator, and Phase 1C must validate shutdown lifecycle.

[CONFIRMED] `AGENTS.md` requires deterministic preview where possible, apply against the same plan/fingerprint where feasible, target ownership checks, destructive idempotency expectations, and engine code independent of Pode.

## 3. Historical console baseline

Reference repository is read-only: `atsisqual/SISQUALManagementConsole` at commit `9756ba956842884fabcf25b82c4fbf1d11cf56bd`.

[CONFIRMED] `Governance.razor` describes active environment locks and says conflicting destructive operations are blocked at SQL level. It also queues work through the database-backed operations repository.

[CONFIRMED] `Jobs.razor` exposes durable job states/history and allows an operator to cancel a job only while its status is `QUEUED`. Running jobs are observed through the central job/worker model; this is not a generic proof of safe mid-operation cancellation.

[CONFIRMED] The old web layer commonly passes `CancellationToken.None` when queueing or querying jobs. Repository method cancellation tokens therefore demonstrate request cancellation plumbing, not engine-level rollback semantics.

[CONFIRMED] The old folder-copy UI explicitly asks the operator to confirm controlled runtime shutdown and revalidation before replacement. This is useful behavioral evidence for a safe-stop requirement, but that workflow depends on the old durable SQL plan/job system.

### What ports and what does not

- Retain: conflicting destructive work is blocked; operations have identities and observable terminal states; cancellation is explicit; destructive plans are revalidated.
- Do not port: SQL-owned locks, job tables, schedules, approvals, leases or worker persistence. ADR-0007 removes the runtime management database.
- Do not infer: a running destructive operation is safely cancellable merely because the old UI can cancel queued jobs.

## 4. Candidate coordinator model

[PROPOSED] The application owns one in-memory coordinator for its lifetime.

Each accepted operation has:

- `OperationId` generated by the coordinator;
- exact `EngineCode`, `Mode` and `InstanceCode`;
- exact lowercase `PlanFingerprint` for APPLY, or no plan fingerprint for PREVIEW;
- request fingerprint derived from engine, mode, instance, plan, cancellation mode and canonical lock set;
- SHA-256 of the raw idempotency key, never the raw key in snapshots/loggable output;
- cancellation mode `COOPERATIVE` or `NONE`;
- canonical lock keys and lifecycle timestamps/status.

[PROPOSED] The raw idempotency key exists only in coordinator memory and is used as an in-process dictionary key. Process restart intentionally forgets it, consistent with ADR-0007.

## 5. Idempotency and locks

[PROPOSED] A request with the same idempotency key and identical request fingerprint returns the original `OperationId`, whether the operation is running or terminal. It does not execute again.

[PROPOSED] Reusing that key with a different mode, plan or other request-fingerprint input fails with `IDEMPOTENCY_CONFLICT`.

[PROPOSED] Mutable instance operations automatically hold `INSTANCE:<InstanceCode>` plus any explicit shared-resource locks. Additional locks are sorted with ordinal comparison so acquisition order is deterministic.

[PROPOSED] A conflicting lock rejects the new operation with `LOCK_CONFLICT`; no idempotency reservation is created for a request that never starts.

[PENDING] The exact shared lock names per engine belong in each engine specification, not in this generic coordinator.

## 6. Preview/apply relationship

[CONFIRMED] The spike distinguishes `PREVIEW` and `APPLY` as operation modes and includes mode in the idempotency request fingerprint.

[CONFIRMED] PREVIEW can execute without a `PlanFingerprint`. The coordinator records the mode and leaves the plan fingerprint empty.

[CONFIRMED] APPLY requires the already confirmed lowercase SHA-256 `PlanFingerprint` matching the existing contract form `^[0-9a-f]{64}$`; it is immutable in the operation record and included in the idempotency fingerprint.

[PROPOSED] The coordinator does not compute or independently validate engine plans. Each mutable engine remains responsible for deterministic preview where feasible, stale-plan/precondition checks before apply, and producing the fingerprint supplied to the coordinator.

## 7. Cancellation semantics

[PROPOSED] Cancellation is cooperative only. A cancellable engine must define safe points and observe the coordinator token there.

[PROPOSED] `NONE` means the coordinator must not attempt to stop/kill that operation. This is the safe default for an operation whose rollback/cancellation semantics are not proven.

[PROPOSED] Repeated cancellation is idempotent. Terminal operations remain terminal.

[CONFIRMED] The spike does not call `PowerShell.Stop()` or kill a worker pipeline as an operational cancellation mechanism.

## 8. Controlled shutdown

[PROPOSED] Shutdown is two-stage:

1. stop admission immediately (`SHUTTING_DOWN` for new requests);
2. optionally request cooperative cancellation, then wait for active operations to reach terminal state.

[PROPOSED] If a non-cancellable or unresponsive operation remains active at the deadline, shutdown returns `ReadyToExit=false` with active operation IDs. The coordinator refuses to close. The application must remain alive and tell the operator which operations block exit.

[PROPOSED] No force-exit path belongs in the coordinator. An external process kill or OS termination is outside this graceful-shutdown guarantee.

## 10. Required gates

The report schema is `SISQUAL_PHASE1C_OPERATION_COORDINATOR_V1`.

Both `windows-2022` and `windows-2025` must prove at least:

- lowercase plan-fingerprint contract;
- first operation accepted;
- duplicate while running returns the same `OperationId`;
- same key with changed plan or changed mode is rejected;
- same-instance conflict is locked out;
- different instances can run concurrently;
- duplicate executes the worker exactly once;
- replay after success does not mutate again;
- instance lock releases after terminal state;
- PREVIEW can execute without a confirmed APPLY fingerprint;
- shared-resource lock blocks a different instance and later releases;
- concurrent terminal readers do not double-finalize the pipeline;
- explicit cooperative cancel reaches `CANCELLED` before simulated mutation;
- non-cancellable cancel is rejected;
- shutdown cancels/drains cooperative work;
- shutdown stops admission;
- non-cancellable active work blocks exit;
- coordinator refuses force-close while active;
- exit becomes ready only after active work drains;
- APPLY plan fingerprint survives unchanged;
- terminal reads remain stable;
- raw idempotency keys are absent from the report.
